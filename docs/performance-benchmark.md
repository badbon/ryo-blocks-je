# External packaged-JAR performance contract

`performance/runner` is a Loom launch project with no mod source. The orchestrator puts supplied jars into an isolated profile's `mods` directory; it never changes the product build graph. `performance/benchmark` remaps a separate client-only harness jar. It observes render-loop CPU time and `Window.swapBuffers`, and uses an eight-query non-blocking `GL_TIME_ELAPSED` ring when OpenGL supports it.

Results are explicitly **hidden-window uncapped render-submission/GPU execution throughput**, never displayed or presented FPS. The harness itself sets `GLFW_VISIBLE=false` immediately before window creation, including for historical JARs. It locks 1280x720, FOV 70, 12-chunk render/simulation distance, noon, clear weather, VSync off and a benchmark-only 10,000 FPS cap override. Warm-up and measurement use fixed monotonic wall-clock durations (defaults 20s and 60s; shorter values are diagnostic-only). Each run writes raw `frames.csv`, `report.json`, an immutable staged-profile manifest, copied `latest.log`, one pre/post low-overhead host snapshot, and one native-framebuffer screenshot captured after the measured window. The harness records observed framebuffer, FOV, distances, VSync, and cap, and refuses a mismatch before sampling. The runner fails closed on profile hashes, mod/log identities, observed settings, missing screenshots, or report/profile contamination.

`comparison.json` records each variant's submitted-FPS run array, median-of-run FPS, and `((currentMedian / baselineMedian) - 1) * 100`. It can pass acceptance only with three or more clean matched pairs and at least 20% improvement; a single pair is explicitly `diagnosticOnly`. `comparison.md` is the concise human-readable equivalent. CPU render samples and non-blocking GPU query samples remain separate; the harness never waits for an unready GPU query.

Build the harness:

```powershell
.\gradlew.bat --no-daemon -p performance :benchmark:remapJar
```

Run Layer 3 only after the historical baseline artifact stack is available:

```powershell
.\tools\run_ryo_performance.ps1 -BaselineJar <historical-ryo.jar> -CurrentJar .\build\libs\ryo-blocks-1.1.0.jar -FabricApiJar <fabric-api.jar> -HarnessJar .\performance\benchmark\build\libs\ryo-performance-harness-1.0.0.jar -BaselineIris <iris.jar> -BaselineSodium <sodium.jar> -BaselineIndium <indium.jar> -BaselineShaderpack <shaderpack.zip> -BaselineConfig <iris.properties> -WorldSource <immutable-world-folder> -OutputRoot C:\Users\Go4No\Documents\Codex\ryo-performance
```

The shipping current profile contains the product jar alone on Fabric Loader; its four required Fabric API modules are nested in that jar. The external benchmark harness compiles against only `fabric-api-base` and `fabric-lifecycle-events-v1` and declares those exact module IDs. It does not nest either module. In a benchmark profile, the current product supplies them, so current stages exactly two standalone mod files: product plus harness. The historical baseline still stages six files: product, harness, the mandatory external full Fabric API jar, Iris, Sodium, and Indium. `-FabricApiJar` therefore remains mandatory but is copied only into baseline stages. Profile manifests record the sorted standalone file hashes and whether the external Fabric API was staged. Benchmark profiles are disposable under ignored `performance-runs/`; selected reports belong in the caller-supplied output root.

## Current terrain-submission candidate

The product now contains a fail-closed shared-buffer/multi-draw candidate for solid, cutout-mipped, and cutout terrain. It mirrors only Minecraft's standard sequential quad uploads with the exact 32-byte `POSITION_COLOR_TEXTURE_LIGHT_NORMAL` format. Visible commands are rebuilt only when visible-section identity/order or committed upload generation changes. Commands remain in original order and are split only into contiguous arena/coordinate-page runs. Translucent and tripwire data are never accepted by the candidate.

This candidate has deterministic source-level proof for allocator first-fit/coalescing, upload/visibility generation invalidation, contiguous command ordering, coordinate/base-vertex arithmetic, lifecycle fallback, and exclusion of translucent layers. It also memoizes `LightingProvider.isLightingEnabled` by provider identity, provider-owned mutation generation, and `ChunkSectionPos.withZeroY`. Yarn 1.20.1 source confirms both block and sky `LightStorage.isSectionInEnabledColumn` checks normalize to that same X/Z column key, the private `enabledColumns` sets mutate only through `LightStorage.setColumnEnabled`, and the provider's client mutation entry points cover enable/disable and propagation. The volatile generation increments after those mutations return; a mutation therefore invalidates cached membership before the next query. Tests cover cross-call same-column reuse at one generation, different-column independence, generation/provider/lifecycle invalidation, and exact true/false provider-result preservation. `compileClientJava`, `compileTestJava`, the focused assertion suite, and the full Gradle build/remap checks pass. The remapped product jar intentionally nests exactly four required Fabric API module jars (`fabric-api-base`, `fabric-lifecycle-events-v1`, `fabric-rendering-v1`, and `fabric-resource-loader-v0`) and no unrelated nested jars; its dependency metadata and Gradle packaging declarations changed accordingly.

No new Minecraft, JFR, benchmark, or capture run was made for this implementation. The existing unloaded samples measured the current package at 458–490 submitted FPS. The source-supported multi-draw candidate targets 16.6–22.6 percentage points of removable `renderLayer` work. The steady fixed-world JFR windows attributed another 7.7–8.1% to lighting-column membership. The generation-owned cache retains the first query for each provider generation but targets the repeated steady-frame membership work, so the existing-sample planning estimate combines **24.3–30.7 points** rather than claiming the provider query itself disappears. That projects approximately **605–707 submitted FPS**, with the range midpoint near **656 FPS**. It is about **11.0–29.7% above** the 545.2334 baseline and **7.5% below to 8.1% above** the 654.2801 target. These are **existing-sample estimates**, not validated results; the external packaged-JAR campaign above remains the required acceptance proof when a runtime campaign is authorized.
